# DBLens M2 · RuoYi-Cloud 用户与权限接入设计

- 日期：2026-04-24
- 状态：Draft approved for planning
- 适用范围：DBLens M2，RuoYi-Cloud 外链接入，用户识别与连接维护权限控制

## 1. 背景与目标

当前 DBLens 已完成 M1 的核心能力：连接管理、库表浏览、SQL 编辑与执行、表格数据操作。M2 需要补齐“用户与权限”，但本次不采用工具内部独立账号体系，而是复用现有 `RuoYi-Cloud` 登录态与角色体系。

本次目标是：

- 将 DBLens 以 `RuoYi-Cloud` 外链菜单方式接入，尽量不修改 RuoYi 代码。
- 所有已登录 RuoYi 用户都可以打开并使用 DBLens。
- 只有管理员可以新建、编辑、删除、测试连接配置。
- 从 M2 开始统一沉淀操作者身份上下文，为 M3 的 `SQL 历史`、`操作日志审计`、`慢查询分析` 提前打好基础。

本次不做：

- 工具内部注册、登录、找回密码、OAuth。
- 按用户分配连接。
- 只读用户 / 普通用户 / 超级管理员三层完整 RBAC。
- 目标数据库用户管理（GRANT / REVOKE / 创建数据库用户）。
- M3 页面本身，例如 SQL 历史列表、审计查询页面。

## 2. 约束与前提

### 2.1 已确认约束

- `RuoYi-Cloud` 源码位于 `E:\RuoYi-Cloud-master`。
- 线上 RuoYi 统一访问入口为 `http://192.168.0.140/`，后端 API 代理前缀为 `http://192.168.0.140/prod-api/`。
- RuoYi 获取当前用户信息接口为 `GET /system/user/getInfo`。
- 菜单系统支持外链菜单，`SysMenu.isFrame` 已具备外链能力。
- 当前 DBLens 后端尚无用户体系，只有连接、查询、数据浏览相关接口。

### 2.2 设计原则

- 优先复用 RuoYi 的认证与角色，不重复做一套账号系统。
- 优先通过菜单配置和部署配置完成接入，而不是修改 RuoYi 前后端逻辑。
- 权限判断必须以后端为准，前端只做展示和交互约束。
- M2 的新增边界必须服务于 M3，避免后续为审计返工认证链路。

## 3. 方案选择

### 3.1 备选方案

#### 方案 A：RuoYi Token 校验 + DBLens 本地权限门控

DBLens 前端从 RuoYi 外链打开后，请求 DBLens 自身的 `/api/auth/me`。DBLens 后端使用当前请求里的 RuoYi token 去调用 `RuoYi /system/user/getInfo`，解析用户身份与角色，再决定 DBLens 的可用能力。

优点：

- 对 RuoYi 改动最小，只需新增外链菜单。
- DBLens 能保持独立应用形态。
- 权限边界清晰，M3 可直接复用用户上下文。

缺点：

- DBLens 后端需要依赖 RuoYi 当前用户信息接口。

#### 方案 B：网关或 Nginx 注入用户头

由网关或代理层将当前用户身份注入请求头，DBLens 直接信任代理传来的用户上下文。

优点：

- DBLens 不必主动请求 RuoYi 用户信息接口。

缺点：

- 需要额外修改网关或 Nginx 配置并处理头部信任边界。
- 安全边界更复杂，不符合“尽量不修改 ruoyi-cloud”。

#### 方案 C：共享 Cookie / SSO 深度接入

将 DBLens 更深地接入 RuoYi 单点登录体系，直接识别同域登录状态。

优点：

- 从产品视角最统一。

缺点：

- 改造成本最高。
- 与当前 M2 的最小可行目标不匹配。

### 3.2 结论

采用 **方案 A：RuoYi Token 校验 + DBLens 本地权限门控**。

这是当前改动最小、边界最清晰、最适合后续演进到 M3 的方案。

## 4. 目标用户与权限模型

本次 M2 不实现完整角色矩阵，只实现与当前业务目标匹配的最小权限模型。

### 4.1 用户来源

所有用户均来自 `RuoYi-Cloud`，DBLens 不维护独立用户表作为认证来源。

### 4.2 权限档位

#### 管理员

判定方式：

- RuoYi 返回角色中包含 `admin`，或
- RuoYi 返回用户可被明确识别为管理员。

能力：

- 查看所有连接。
- 新建连接。
- 编辑连接。
- 删除连接。
- 测试连接配置。
- 打开连接并使用所有 M1 功能。

#### 普通已登录用户

能力：

- 查看所有已配置连接。
- 打开连接。
- 浏览数据库结构。
- 使用 SQL 编辑器与数据浏览功能。
- 不允许新建、编辑、删除、测试连接配置。

### 4.3 明确不做

- 不按用户分配连接。
- 不按部门分配连接。
- 不区分“普通用户”和“只读用户”。
- 不在 M2 中引入更细粒度的 SQL 写权限控制。

## 5. 总体架构

### 5.1 RuoYi 侧

RuoYi 只承担两个职责：

- 为 DBLens 提供访问入口。
- 为 DBLens 提供已登录用户身份来源。

落地方式：

- 在菜单中新增一个外链菜单，指向 DBLens 发布地址。
- 菜单可见性继续使用 RuoYi 自己的角色/菜单授权体系控制。

本次不要求修改 RuoYi 前端路由逻辑，不要求新增专门的 DBLens 嵌入页。

### 5.2 DBLens 前端

DBLens 前端增加一个“当前用户初始化”流程：

- 应用启动时先请求 `/api/auth/me`。
- 请求成功后将 `userId`、`userName`、`roles`、`isAdmin` 存入新的认证 store。
- 页面上的“新建连接”“编辑连接”“删除连接”“测试连接”等入口根据 `isAdmin` 控制显示与可用状态。

如果 `/api/auth/me` 返回未登录或无效身份：

- 不展示业务操作页面。
- 展示“请从 RuoYi 登录后进入 DBLens”的引导页或错误页。

### 5.3 DBLens 后端

DBLens 后端新增统一的“当前 RuoYi 用户解析层”：

- 从请求中提取 token。
- 调用 `RuoYi /system/user/getInfo`。
- 将返回结果映射为 DBLens 内部的 `CurrentUser` 结构。
- 路由层通过依赖项拿到 `CurrentUser`，再做权限判断。

关键原则：

- 不信任前端传来的角色信息。
- 管理员判定、连接维护权限，必须由后端执行。

## 6. 认证与身份流

### 6.1 请求流

1. 用户登录 RuoYi。
2. 用户从 RuoYi 外链菜单打开 DBLens。
3. DBLens 前端发起 `/api/auth/me` 请求。
4. DBLens 后端读取当前请求中的 RuoYi token。
5. DBLens 后端调用 `http://192.168.0.140/prod-api/system/user/getInfo`。
6. RuoYi 返回 `user`、`roles`、`permissions`。
7. DBLens 将结果映射为内部用户对象并返回给前端。

### 6.2 DBLens 内部用户对象

建议统一映射为：

- `userId`
- `userName`
- `nickName`
- `roles`
- `permissions`
- `isAdmin`

其中：

- `isAdmin` 由 DBLens 后端根据 RuoYi 角色或管理员判定逻辑统一计算。
- 前端只消费这个标准结构，不直接依赖 RuoYi 原始返回格式。

### 6.3 失败处理

#### token 缺失

- `/api/auth/me` 返回未认证状态。
- 前端提示需要从 RuoYi 登录后访问。

#### token 无效或过期

- DBLens 后端返回 401。
- 前端显示“登录状态失效，请回到 RuoYi 重新进入”。

#### RuoYi 用户信息接口不可用

- DBLens 后端返回 502 或服务不可用错误。
- 前端展示“用户信息校验失败，请稍后再试”。

## 7. 路由与权限策略

### 7.1 新增公共认证接口

新增：

- `GET /api/auth/me`

职责：

- 校验当前 RuoYi 登录态。
- 返回 DBLens 统一用户结构。

### 7.2 连接相关接口分级

#### 所有已登录用户可用

- 查看连接列表
- 查看单个连接
- 打开连接
- 断开连接
- 浏览数据库/表/字段
- 执行 SQL
- 数据浏览与数据编辑功能

#### 仅管理员可用

- 新建连接
- 编辑连接
- 删除连接
- 测试表单连接
- 测试已保存连接

### 7.3 前端交互约束

前端将根据 `isAdmin` 做以下处理：

- 非管理员隐藏“新建连接”按钮。
- 非管理员隐藏连接项的编辑/删除入口。
- 非管理员无法触发测试连接表单。

但这些都只是体验优化，不构成真正权限防线。真正限制由后端接口依赖控制。

## 8. 数据与模型调整

M2 不新增工具内部登录用户表作为认证来源，但需要为后续审计留出统一操作者上下文。

### 8.1 当前用户上下文结构

后端服务层建议统一接收或能访问以下上下文：

- `operator_user_id`
- `operator_username`
- `operator_roles`
- `operator_is_admin`

### 8.2 M2 不新增但需考虑的记录字段

虽然 M2 不实现完整历史与审计页面，但所有关键操作的设计要允许后续记录：

- `connection_id`
- `database_name`
- `action_type`
- `statement_text` 或 `statement_summary`
- `success`
- `error_message`
- `started_at`
- `finished_at`
- `operator_user_id`
- `operator_username`
- `operator_roles_snapshot`

这些字段不是要求 M2 全部落库，但 M2 的服务边界必须允许未来无痛接入。

## 9. 面向 M3 的预留设计

### 9.1 SQL 历史

M3 的 SQL 历史记录将依赖 M2 已建立的用户上下文，因此 M2 中：

- 查询执行入口必须能够拿到当前操作者。
- SQL 执行服务层不能假设“匿名用户”。

### 9.2 操作日志审计

M3 的写操作审计将依赖 M2 的统一操作者身份，因此 M2 中：

- 连接维护操作就应当经过统一权限依赖。
- 未来数据写入、DDL 操作可以直接复用同样的身份来源。

### 9.3 慢查询分析

慢查询记录未来需要按用户维度聚合，因此当前的身份映射字段不能只保留“是否管理员”，必须至少保留：

- `userId`
- `userName`
- `roles`

## 10. 接入与部署设计

### 10.1 RuoYi 接入方式

优先采用菜单配置完成接入：

- 在 RuoYi 系统菜单中新增一个外链菜单。
- `path` 指向 DBLens 发布地址。
- `isFrame` 设置为外链。
- 菜单授权按现有 RuoYi 角色配置。

本次不要求修改 `ruoyi-ui` 代码，只需要使用其已有外链菜单能力。

### 10.2 DBLens 部署方式

建议保持 DBLens 独立部署：

- 前端构建为静态资源，由现有 Nginx 托管。
- 后端以独立 Python 进程运行。
- Nginx 为 DBLens 提供独立访问路径或独立站点。

推荐访问链路：

- 用户访问 RuoYi 页面。
- 从 RuoYi 外链菜单跳到 DBLens 地址。
- DBLens 后端反向请求 `RuoYi /prod-api/system/user/getInfo` 获取当前用户。

### 10.3 跨域与 token 传递

M2 计划中必须明确处理：

- DBLens 与 RuoYi 是否同域或同主域。
- token 是通过 header 透传还是浏览器已有请求头复用。
- DBLens 请求 RuoYi 用户信息接口时如何带上当前用户 token。

本设计要求实施阶段优先选择“最少改动、最稳定”的 token 透传方式，并在实施计划中明确具体机制。

## 11. 影响范围

预计影响 DBLens：

- 后端配置层
- 后端认证/依赖层
- 连接相关路由
- 前端应用初始化流程
- 前端连接管理 UI 权限展示
- 前端新增认证 store

预计影响 RuoYi：

- 菜单数据配置
- 部署配置或 Nginx 路由配置

预计不修改或尽量不修改：

- `RuoYi-Cloud` 核心前端源码
- `RuoYi-Cloud` 核心后端业务代码

## 12. 风险与应对

### 12.1 风险：DBLens 无法可靠拿到 RuoYi 当前 token

应对：

- 将 token 透传机制作为实施前置验证项。
- 在计划阶段单独验证外链场景下 token 的可达性。

### 12.2 风险：RuoYi 外链菜单只是简单跳转，无法天然共享请求头

应对：

- 在实施中优先验证当前浏览器登录态与 DBLens 域名/路径关系。
- 若直接复用失败，再设计最小补充机制，但不在本 spec 中预设更重的网关改造。

### 12.3 风险：前端只隐藏按钮但后端未拦截

应对：

- 所有连接维护能力必须使用统一管理员依赖做后端拦截。

### 12.4 风险：M3 再做审计时需要返工

应对：

- M2 统一引入 `CurrentUser` 与操作者上下文。
- 服务边界从一开始就面向“可记录操作者”设计。

## 13. 验收标准

满足以下条件视为 M2 本阶段设计落地成功：

- RuoYi 中可通过外链菜单打开 DBLens。
- 已登录 RuoYi 用户能进入 DBLens 并正常使用现有工具能力。
- 非管理员无法新建、编辑、删除、测试连接配置。
- 管理员可以维护连接配置。
- DBLens 后端可稳定识别当前 RuoYi 用户身份。
- M2 的后端身份模型可直接复用到 M3 的 SQL 历史和操作日志审计。

## 14. 后续实施建议

实施计划建议分为以下几个子任务：

1. 验证外链菜单打开 DBLens 时的 token 透传路径。
2. 新增 DBLens `auth/me` 接口与 `CurrentUser` 依赖。
3. 将连接维护接口切换为管理员保护。
4. 新增前端认证 store 与管理员 UI 控制。
5. 在 RuoYi 中配置外链菜单并完成联调。
6. 预埋 M3 所需的操作者上下文传递边界。
